# 設計の原則

カタログの中身と作り方についての決まりと、その理由です。

## 中身の原則

| 原則 | なぜ |
|---|---|
| **出典で確かめられる範囲だけを書く** | カタログは提案や社内説明に引用される。出典に無いことが混ざると、引用した人が困る |
| **一次資料を優先する** | 二次情報（解説記事・検索結果の要約）は、要約の段階で意味が変わっていることがある |
| **読み取れない項目は「調査中」** | 空欄だと「書き忘れ」と「わからない」の区別がつかない。推測で埋めると誤りが残る |
| **読めなかった出典は、そう書く** | 出典に載っていても、本文を確かめていないことを読む人が知れるように（例：ボット対策で開けなかったページ） |
| **断定を避け、出典の言葉と解釈を分ける** | 「〜とされている」「〜と報告されている」は出典の記述、「〜と考えられる」は解釈。根拠の強さを読む人が判断できる |
| **summary は課題、value_proposition は解決と成果** | 2つを並べて読むと「何が問題で、PETs でどう解決し、何が得られたか」がわかるように |
| **タイトルに技術名を入れない** | 技術は `technology_category` で分類する。タイトルは「誰の、どんなデータを、どう守って、何を実現したか」を表す |
| **1つの取り組みを1つの事例にする** | 複数の取り組みを混ぜると、出典との照合ができなくなる |

## データの原則

| 原則 | なぜ |
|---|---|
| **1事例 = 1ファイル** | 変更の差分が事例ごとに分かれ、レビューしやすい。コンフリクトも起きにくい |
| **事例 ID は UUID** | 連番だと、並行して事例を作ったときにぶつかる |
| **`index.json` は手で書かない** | ビルドのたびに作り直すので、追加し忘れ・消し忘れが起きない |
| **機微な情報を入れない** | 公開情報だけを扱う。個人情報や顧客情報は入力しない（画面の About にも書いている） |

## 作り方の原則

| 原則 | なぜ |
|---|---|
| **人の目が入っていないものは「未レビュー」と表示する** | 読む人が割り引いて読めるように。事例も参考資料も同じ（[事例の作り方とレビューの仕組み](review-lifecycle.md)） |
| **相手が機械向けに出している入口を使う** | ボット対策を回避しない。RSS・API・PDF 版を探す（[事例集からまとめて取り込む](../howto/import-from-repository.md)） |
| **範囲の違う変更は PR を分ける** | 事例の追加と CI の修正を混ぜると、レビューもロールバックもしにくい（PR #233 と PR #242） |
| **ドキュメントはコードと同じ PR で直す** | 後回しにすると、食い違いが残り続ける |
