# これまでの判断と失敗

新しいものが上です。足すときは[ドキュメントを書く](../howto/write-docs.md)の形に従います。

## 2026-11 参考資料（読んだほうがいいもの）のデータを作った

- **決めたこと**：事例とは別に、事例集・当局のガイド・報告書・標準などの「参考資料」を、1件 = `public/resources/<id>.json` で持つ（Issue #244）
- **なぜ**：OECD のリポジトリでは23件のうち12件が事例ではなく文書だった。PETs を検討する人が次に読むべきものとして価値があるが、事例の形には収まらない
- **どうした**：
  - 置き方は事例と同じ「1件 = 1ファイル」。並行して足しても衝突しにくい
  - `id` は UUID ではなく読める名前にした。人が書き、参照するため
  - `review_status` を持たせた。説明文も AI が書くことが多く、事例と同じ誤りが起きうるため
  - 事例集からの取り込み状況（`import_status`・`import_note`）を同じデータに持たせたが、利用者の画面には出さない
  - 事例とのつながり（事例の出典から参考資料を指す関係）は作らなかった
  - 事例の検査は必須項目しか見ていないが、参考資料の検査は最初から Zod スキーマで全項目を見る
  - 初版の14件は、本文を開いて確かめた範囲で書いた。公開日は検索結果の要約ではなく本文で確かめた（例：ICO の導入障壁の報告書は、ページに公開日が無いため年だけを書いた）
- **今の決まり**：[参考資料を1件追加する](../howto/add-resource.md)、[参考資料の形式](../reference/resources-json.md)

## 2026-11 ドキュメントの閲覧ページは raw.githack.com で見ることにした

- **決めたこと**：`docs/index.html`（閲覧ページ）と `docs/slides.html` は、raw.githack.com を通して `develop` のファイルをそのまま表示して読む（https://raw.githack.com/pwscup/pets-usecase-catalog/develop/docs/index.html）
- **なぜ**：GitHub Pages は1リポジトリにつき1サイトで、本番のカタログが使っている。方針でドキュメントは本番に出さない。開発用のリポジトリを別に作って配信する案もあったが、まだ閲覧ページがどう使われるかわからない段階で、リポジトリと鍵の管理を増やすのは早いと判断した。raw.githack.com なら設定もデプロイも要らない
- **割り切り**：外部の無料サービスに頼る（止まることがある、反映に数分かかる）。見られるのはドキュメントだけで、`develop` のアプリの画面は見られない
- **見直す条件**：閲覧ページをチームで日常的に使うようになったら、または `develop` のアプリの画面も確認したくなったら、開発用リポジトリの GitHub Pages に `develop` のビルドと `docs/` を送る仕組みに移す
- **今の決まり**：[ドキュメントを書く](../howto/write-docs.md)の「公開先」、[環境と自動処理](../reference/environments.md)

## 2026-11 開発者ドキュメントを4種類に分けて作り直した

- **決めたこと**：`docs/` を Diátaxis の4種類（チュートリアル・ハウツー・リファレンス・解説）に分け、入口・用語集・スライド・閲覧ページを置いた。`CLAUDE.md` は短くし、`docs/` を指すだけにした
- **なぜ**：それまでの `docs/CONTRIBUTING.md`・`docs/spec.md`・ルートの `README.md` は、コードと食い違っていた。たとえば `README.md` のテンプレートには、今は無い `synthetic_generation_method` が載り、`domain` は4種類（実際は9種類）だった。`spec.md` は LocalStorage とのマージを前提にしていたが、その仕組みはもう無い
- **どうした**：
  - リファレンスをコードから書き起こした。食い違ったらコードが正
  - `docs/spec.md` は、初版の仕様としてこの記録（下の「2026-02」）にまとめて消した
  - `docs/prompts/` は `src/constants/prompts.ts` と中身がずれ始めていた（タイトルの「40〜60文字」の目安が Markdown 側に無いなど）。原本を `prompts.ts` の1つにするため消した
  - `docs/REVIEW_WORKFLOW.md` は [事例をレビューする](../howto/review-case.md) に移し、画面からのリンクも直した
  - `/case-create` のスキルが「連番で採番」「`index.json` に手で追加」と書いていたのを、UUID で採番し `index.json` は触らない、に直した（実際の運用に合わせた）
- **見つかったこと（未対応）**：
  - `npm run validate` は `tsx` が依存に無いため動かない。手順はすべて `npx tsx scripts/validate-cases.ts` にした
  - 画面の「GitHubで提出」は `main` を開く。PR の base を `develop` に変えるよう手順に書いた
  - `src/constants/styles.ts` の `TECHNOLOGY_CATEGORY_COLORS` に `distributed_analytics` が無い
  - 画面のリンクの一部が、リポジトリの旧名（`syntheticdata-usecase-catalog`）のまま
- **今の決まり**：[ドキュメントを書く](../howto/write-docs.md)

## 2026-11 CI が全 PR で落ちた（Ubuntu 26.04）

- **起きたこと**：GitHub の `ubuntu-latest` が Ubuntu 26.04 を指すようになり、Playwright 1.58.2 がブラウザを入れられず、`develop` を含むすべての PR で CI が赤くなった
- **なぜ**：ランナーの OS を `ubuntu-latest` で指定していたため、GitHub 側の更新がそのまま影響した
- **どうした**：事例追加の PR（#233）には混ぜず、別の PR（#242）で `runs-on: ubuntu-24.04` に固定して先にマージした。#233 には `develop` を取り込んだ
- **今の決まり**：[CI が落ちたとき](../howto/fix-ci.md)。Playwright が対応したら上げて `ubuntu-latest` に戻す

## 2026-11 事例集（OECD PETs リポジトリ）からの取り込みと、そこで起きた失敗

- **起きたこと**：OECD の PETs リポジトリ（2026-10 公開）の事例11件を取り込んだ（PR #233、Issue #232）。サイトはボット対策で自動では開けなかった
- **どうした**：
  - 回避はせず、OECD が出している RSS（`api.oecd.org`）を使って一覧を取った
  - 既収録の4件には、OECD を出典とタグで追記した。未収録の6件を一次資料から作った
  - OECD の文書に含まれる UN ガイドの18事例も照合し、未収録の8件をサブ Issue（#234〜#241）にした
- **失敗**：`case-reviewer` のレビューで、次の誤りが見つかった

  | 誤り | 原因 |
  |---|---|
  | 英米の小児がんパイロットに、NIST の別プロジェクトのレッドチーミングを書いた | 検索結果の要約を、一次資料に書いてあるものと思い込んだ |
  | シンガポールの病院の事例に、同じ研究者のポスターの数値を PoC の結果として書いた | 関連研究を同じ実験とみなした |
  | PoC を「実現」と書いた、出典の「概ね」を落とした | 文を自然に整える過程で、限定が抜けた |

- **共通の原因**：二次情報や関連資料を、一次資料と同じ重さで扱った
- **今の決まり**：一次資料を優先し、関連資料は「関連研究」と書き分ける（[設計の原則](principles.md)、[事例集からまとめて取り込む](../howto/import-from-repository.md)）

## 2026-04 AI 生成の事例を人がレビュー済みにする流れを作った

- **決めたこと**：画面の編集フォームから、チェックリストを確かめて事例をレビュー済みにできるようにした（PR #106）。既存の事例の確認点を1件ずつ Issue にした（Issue #183〜#214、ラベル `review-triage`）。`review_status` という項目自体は、2026-03 の PETs への拡張で入っていた
- **なぜ**：AI が作った事例と、人が確かめた事例の区別が、読む人にわからなかった
- **今の決まり**：[事例をレビューする](../howto/review-case.md)

## 2026-04 「GitHubで提出」で既存の事例を開くようにした

- **起きたこと**：編集画面の「GitHubで提出」が、既存の事例でも新規作成の画面を開いていた
- **なぜ**：新規作成と編集で、開く URL を分けていなかった
- **どうした**：既存の事例は GitHub の編集画面を開くようにした（PR #97）
- **今の決まり**：どちらも `main` を開くので、PR の base を `develop` に変える（[事例をレビューする](../howto/review-case.md)、[画面と URL](../reference/url.md)）

## 2026-03 重複事例を統合した

- **起きたこと**：最初期の事例（`seed-*`）と、のちに別の事例集から取り込んだ事例（`fpf-*`・`rpt-*`）に、同じ取り組みが重複していた
- **どうした**：5件を統合・削除し、出典は残る側に移した（PR #92、Issue #87）。課題と価値の表現の重複も整理した（PR #104）
- **今の決まり**：取り込みの前に重複を確かめる（[事例を1件追加する](../howto/add-case.md)）。まだ重複の疑いが残っているものがある（Issue #232 のコメント）

## 2026-03 英国 CDEI のガイドから46件をまとめて取り込んだ

- **決めたこと**：英国 CDEI の PETs Adoption Guide に載っている国外の事例を、まとめてカタログに入れる
- **なぜ**：合成データ以外の PETs の事例を、まとまった数で集めるため
- **どうした**：`scripts/generate-cdei-cases.py` で事例を case.json にした（PR #80）
- **今の決まり**：このスクリプトはこの取り込みのためのもの。その後の事例集（OECD・UN）は、照合して1件ずつ作っている（[事例集からまとめて取り込む](../howto/import-from-repository.md)）

## 2026-03 合成データのカタログから、PETs 全般のカタログに広げた

- **決めたこと**：`technology_category` と `review_status` を加え、合成データ以外の PETs も扱うことにした（2026-03-07、PR #34〜#48）。2026-03-09 には技術詳細の項目名を PETs 全般向けに変え、`distributed_analytics` を足して技術カテゴリを6種類にした（#49・#50）
- **その後**：リポジトリ名が `syntheticdata-usecase-catalog` から `pets-usecase-catalog` に変わった（時期は履歴から特定できていない）
- **なぜ**：合成データだけでは、実際の活用事例の多く（秘密計算・連合学習・差分プライバシー）を拾えなかった
- **今の決まり**：`technology_category` が無い古いデータは、読み込み時に `synthetic_data` として扱う（[全体の構成](architecture.md)）

## 2026-03 index.json を自動で作るようにした

- **起きたこと**：`public/cases/index.json` を手で書いていたため、事例の追加し忘れ・消し忘れが起きうる状態だった
- **どうした**：ビルドのたびにフォルダを数えて作り直す Vite プラグインを入れた（`plugins/generate-case-index.ts`、2026-03-04 のコミット `b2e2669`）。その後、Issue #30 でテストを強化した。`index.json` はコミットしない
- **今の決まり**：[ファイルとフォルダ](../reference/files.md)

## 2026-02 初版の仕様（合成データ ユースケースカタログ）

- **決めたこと**：GitHub Pages だけで動く、合成データの事例カタログを作る（旧 `docs/spec.md`）
  - サーバー側の DB と認証は持たない
  - 生成手法・安全性評価・有用性評価を分けて書き、出典に無ければ「調査中」を許す
  - 出典は最低1件
- **その後変わったこと**：
  - 当初は、同梱データ（`seed_cases.json`）と、ブラウザに保存したデータ（LocalStorage）をマージする設計だった。今は事例を1件ずつファイルにし、PR で追加する（ブラウザへの保存は無い）
  - 項目名が変わった（`synthetic_generation_method` → `privacy_enhancement_method`、`safety_evaluation_method` → `safety_assurance_method`、`outcomes` → `value_proposition`）
- **今も続いている決まり**：サーバーを持たない、「調査中」を許す、出典は最低1件（[全体の構成](architecture.md)）
